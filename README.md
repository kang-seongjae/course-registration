# 수강신청 사이트: 동시성·부하 실험 기록

Java 21 + Spring Boot 4.1 + MySQL 8.4(Docker)로 만든 수강신청 사이트를 단계별로 키우면서,
"동시에 몰리는 신청"에서 생기는 문제를 직접 재현하고 → 원인을 측정으로 찾고 → 고치고 → 다시 재는 과정을 기록한 프로젝트다.

**목표:** 정원이 절대 넘치지 않는 수강신청을 만들고, 5,000명이 같은 순간에 접속하는 상황에서 **오류 1% 미만, p95 응답 3초 이내**를 노트북 한 대에서 달성한다.
(결과: 4단계-4에서 달성. 오류 0%, p95 1.6 ~ 2.6초)

## 측정 환경과 조건

| 항목 | 내용 |
|---|---|
| 노트북 | AMD Ryzen 5 4500U (6코어 6스레드), RAM 15.4 GB, Windows 11 Pro |
| Docker Desktop | WSL2, VM 에 CPU 6개 / 메모리 8 GB 할당. MySQL 과 (4단계-3부터) 앱이 여기서 돈다 |
| 서버·DB·부하 발생기 | **전부 이 노트북 한 대**에서 실행. CPU 6코어를 셋이 나눠 쓴다 |
| 데이터 | 강의 10개(정원 합계 151), 학생 5,000명. 로그인 없음 |
| 시나리오 (`load-test/enroll.js`) | 가상 사용자(VU)마다 서로 다른 학생으로 ① 강의 목록 조회 → ② 강의 하나를 무작위로 골라 신청. VU 당 1회, 전원이 동시에 출발 |
| 부하 단계 | 500 / 2,000 / 5,000 VU. 5,000 VU 는 편차가 커서 **3번 측정해 범위로** 적는다 |
| 매 실행 | 전: `reset.sql` 로 신청 데이터 초기화. 후: `verify.sql` 로 정원 초과 0, `enrolled_count` 와 실제 행 수 불일치 0 확인 |
| 함께 기록한 것 | MySQL 행 락 대기 횟수·누적 시간, 문장 종류별 실행 수(performance_schema), 실행 3초 시점 스레드 덤프, PC 전체 CPU(typeperf) |
| 정원 초과 거절(400) | 오류가 아니라 정상 응답으로 집계 |

**4단계-3부터 측정 조건이 바뀌었다.** 3단계 ~ 4단계-2는 앱을 Windows 에서 직접(`java -jar`) 띄우고 k6 도 Windows 에서 돌렸다.
이때 오류는 전부 "connection refused" 였고 원인은 Windows 가 TCP 접속 대기열을 200 으로 제한하는 것이었다.
4단계-3부터는 앱을 **Linux 컨테이너**에서 띄우고, k6 도 **컨테이너로 Docker 네트워크 안에서** 서버에 직접 접속한다.
Windows 의 k6 가 Docker Desktop 포트 포워딩을 거쳐 접속하면 같은 200 제한 때문에 80% 이상 거절되므로, 그 숫자는 서버가 아니라 Docker Desktop 을 재는 것이다.
따라서 4단계-2 이전과 4단계-3 이후의 수치는 "오류 비율"을 직접 비교하면 안 되고, 서버에 실제로 도달한 요청 수를 함께 봐야 한다.

| 4-3 | 오류가 전부 connection refused | Windows 접속 대기열 200 제한 | 앱을 Linux 컨테이너로(accept-count 1000 적용 확인), k6 를 Docker 네트워크 안에서 | 오류 27.6 ~ 38.0% → **0%**. p95 3,827 ~ 5,479 ms (요청 10,000개 전부 처리) |

DB 정합성(정원 초과 0, 인원 불일치 0)은 2단계 수정 이후 모든 실행에서 유지됐다.

## 한계와 다음에 해 볼 것

- **노트북 한 대의 CPU 한계.** 5,000 VU 에서 앱 약 4코어, MySQL 약 1.3코어, k6 약 0.4 ~ 1.2코어를 쓴다. 평균 65% 까지 내렸지만 출발 직후는 여전히 98 ~ 99% 다.
  초당 2,000 ~ 2,400 요청이 이 PC 의 상한이고 설정으로는 안 움직인다.
- **부하 발생기를 다른 머신으로 분리.** k6 가 같은 CPU 를 쓰는 한 서버의 진짜 한계는 알 수 없다. 다른 PC 에서 k6 를 돌려 다시 재 보는 것이 다음 순서다.
- **실제 Linux 서버에 배포.** Windows 접속 대기열 200 제한과 Docker Desktop 포트 포워딩은 이 노트북에서만 있는 경로다. 실제 서버에서는 브라우저 접속도 4단계-3의 "네트워크 안" 결과에 가까울 것이다.
- **남은 병목: 같은 강의 행의 락 줄.** 신청 한 건이 락을 쥔 채 커밋(디스크 쓰기 약 20 ms)하는 동안 뒤의 신청이 기다린다. 캐시가 낡은 1초 동안 들어온 요청이 줄을 더 길게 만든다.
  `innodb_flush_log_at_trx_commit = 2`(장애 시 최근 1초 커밋 유실 가능), 강의가 찼다는 사실을 캐시에 더 빨리 반영, 강의별 앱 내 대기열 등을 시도해 볼 수 있다.
- **서버 여러 대.** 지금의 메모리 캐시는 서버 한 대 기준이다. 여러 대로 늘리면 캐시 공유(Redis 등)와 커넥션 풀 합계(MySQL `max_connections` 151)를 다시 설계해야 한다.

## 배운 점

**1. 문제는 고치기 전에 먼저 눈으로 확인해야 한다**

한 명씩 눌렀을 때는 정원 제한이 잘 동작했다. 그런데 100명이 동시에
신청하자 실제 신청은 23건인데 신청 인원은 13으로 기록됐고(갱신 유실),
77명은 정원 초과가 아닌데도 데드락 오류로 실패했다. 정원 30명을 넘기지
않은 건 코드가 막아서가 아니라 대부분이 오류로 튕겨 나가서 생긴 우연이었다.

**2. 병목은 짐작이 아니라 측정으로 찾는다**

락으로 줄을 세웠으니 락이 느린 원인일 거라고 생각했다. 측정해 보니
락 대기는 신청 한 건당 7ms 정도였고, 진짜 원인은 기본값 그대로인
DB 커넥션 풀 10개였다. 요청 처리 스레드 202개 중 190개가 커넥션을
기다리고 있었다.

**3. 병목은 하나를 풀면 다른 곳으로 옮겨 간다**

커넥션 풀을 50으로 늘리자 행 락 누적 대기가 5초에서 127초로 늘었다.
줄 서는 곳이 풀 앞에서 락 앞으로 옮겨 간 것이다. 이후로도 병목은
커넥션 풀, 행 락, 접속 대기열, CPU 순서로 이동했다.

**4. 코드의 한계와 환경의 한계를 구분해야 한다**

접속 대기열 설정을 5,000으로 올려도 오류가 줄지 않았다. Windows가
대기열을 200개로 제한하기 때문이었다. 서버를 Linux 컨테이너에서 실행하자
같은 코드로 오류가 0%가 됐다. 마지막에 남은 병목은 노트북 CPU였고,
이건 코드로 바꿀 수 없는 부분이었다.

**5. 성능 개선에는 대가가 따른다**

강의 목록을 1초 캐시하자 SELECT가 20,008번에서 약 600번으로 줄고
p95가 3초 이내로 들어왔다. 대신 화면의 신청 인원이 최대 1초 늦게 보이고,
행 락 대기는 오히려 늘었다. 그래서 조금 늦어도 되는 곳(목록 화면)에만
캐시를 쓰고, 정확해야 하는 신청 처리는 DB의 조건부 UPDATE로 판단하게 했다.

**6. 하나를 바꾸면 다른 규칙이 깨지지 않는지 확인한다**

락 구간을 줄이려고 FOR UPDATE를 빼자 같은 학생의 중복 신청을 막던
장치도 함께 사라졌다. 유니크 제약을 추가하고, 같은 학생이 동시에
10번 신청해도 1건만 성공하는 테스트로 확인했다.

**7. 한 번의 측정으로 판단하지 않는다**

같은 설정으로 다시 돌려도 오류 비율이 20~40% 사이에서 흔들렸다.
그래서 5,000 VU는 3번씩 측정해서 범위로 비교했다.

# 수강신청 사이트 (1단계: 기본 기능)

Java + Spring Boot + MySQL(Docker)로 만든 간단한 수강신청 사이트입니다.

## 기능

- 강의 목록 조회
- 수강 신청 (정원이 차면 거절, 같은 강의 중복 신청 거절)
- 수강 신청 취소
- 내 신청 목록 조회
- 시작 시 샘플 강의 10개, 학생 100명 자동 등록

로그인은 없으며, 화면에서 학생 ID(1~100)를 입력해 학생을 구분합니다.

> 1단계에서는 동시성 처리(락 등)를 **일부러 넣지 않았습니다.**
> 여러 요청이 동시에 들어오면 정원 초과나 중복 신청이 발생할 수 있으며, 다음 단계에서 직접 확인하고 고칠 예정입니다.

## 실행 방법

사전 준비: JDK 21, Docker Desktop

```powershell
# 1. MySQL 실행 (처음 한 번만 이미지 다운로드)
docker compose up -d

# 2. 애플리케이션 실행 (처음 한 번은 Gradle과 라이브러리를 내려받느라 시간이 걸립니다)
.\gradlew.bat bootRun
```

브라우저에서 http://localhost:8080 접속.

종료: 애플리케이션은 `Ctrl + C`, MySQL은 `docker compose down`.
(DB 데이터까지 지우려면 `docker compose down -v`)

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/courses` | 강의 목록 |
| GET | `/api/students/{studentId}/enrollments` | 내 신청 목록 |
| POST | `/api/enrollments` | 수강 신청. 본문: `{"studentId": 1, "courseId": 3}` |
| DELETE | `/api/enrollments/{enrollmentId}?studentId=1` | 수강 신청 취소 |

규칙에 어긋나면 `400` 과 함께 `{"message": "..."}` 를 돌려줍니다.

## 2단계: 수정 전 결과

동시성 문제를 확인하기 위한 테스트 `src/test/java/.../EnrollmentConcurrencyTest.java` 를 추가했다.
정원 30명인 강의(CS101)에 서로 다른 학생 100명이 CountDownLatch 로 같은 순간에 신청한다.
실제 MySQL(docker compose)에 대해 실행하며, 매 실행 전 CS101 의 신청 내역을 지우고 인원을 0으로 되돌린다.

```powershell
docker compose up -d
.\gradlew.bat test --tests "*EnrollmentConcurrencyTest" --rerun
```

동시성 처리가 없는 상태에서 3번 실행한 결과:

| 실행 | 신청 성공 | 규칙 거절 | 기타 오류(데드락) | 강의의 신청 인원 (enrolled_count) | 실제 신청 내역 행 수 |
|---|---|---|---|---|---|
| 1회 | 23 | 0 | 77 | 13 | 23 |
| 2회 | 22 | 0 | 78 | 12 | 22 |
| 3회 | 23 | 0 | 77 | 12 | 23 |

테스트는 3번 모두 실패(FAILED). 확인된 문제:

1. **갱신 유실**: 실제 신청 행은 23개인데 `enrolled_count` 는 13. 모든 스레드가 같은 값(0)을 읽고
   각자 1을 더한 뒤 `enrolled_count = <계산한 값>` 으로 덮어쓰기 때문에 다른 스레드의 증가분이 사라진다.
   (`EnrollmentService.enroll` 의 `course.increaseEnrolledCount()` 가 메모리 값만 바꾸고 JPA 가 UPDATE 로 덮어쓴다)
2. **낡은 값으로 정원 검사**: `course.isFull()` 은 자기 트랜잭션이 읽은 시점의 숫자만 본다.
   100개 스레드가 동시에 0을 읽으면 전부 "정원 안 찼음"으로 판단한다. 이번에는 데드락에 가려졌지만
   데드락이 없으면 여기서 정원 초과가 발생한다.
3. **데드락**: `enrollments` 가 `courses` 를 외래 키로 참조하므로 INSERT 시 courses 행에 공유 잠금(S)이 걸리고,
   이어지는 courses UPDATE 는 같은 행의 배타 잠금(X)을 기다린다. 두 트랜잭션이 서로 S 를 쥔 채 X 를 기다려
   MySQL 이 한쪽을 강제 종료한다. (`SHOW ENGINE INNODB STATUS` 로 확인)

정원을 넘기지 않은 것은 로직이 막아서가 아니라 요청의 77% 가 데드락으로 튕겨 나갔기 때문이다.

## 2단계: 수정 후 결과

비관적 락(`SELECT ... FOR UPDATE`)으로 해결했다.

- `CourseRepository.findByIdForUpdate()` 추가: `@Lock(LockModeType.PESSIMISTIC_WRITE)` 를 붙인 조회 메서드.
  실행되는 SQL 은 `select ... from courses c1_0 where c1_0.id=? for update of c1_0`.
- `EnrollmentService.enroll()` / `cancel()`: 강의를 `findById()` 대신 `findByIdForUpdate()` 로 읽는다.

동작 원리: 트랜잭션이 강의 행을 FOR UPDATE 로 읽는 순간 그 행에 배타 잠금(X)이 걸린다.
같은 강의를 처리하려는 다른 트랜잭션은 FOR UPDATE 지점에서 앞 트랜잭션이 커밋될 때까지 기다린다.
그래서 같은 강의에 대한 신청/취소는 한 번에 하나씩만 진행되고,

1. 정원 검사(`isFull`)는 항상 방금 커밋된 최신 값을 본다 → 정원 초과 없음
2. 인원 증가는 앞 트랜잭션의 결과 위에 쌓인다 → 갱신 유실 없음
3. 자기 트랜잭션이 이미 X 잠금을 쥔 상태에서 INSERT(FK 검사의 S 잠금)와 UPDATE 를 하므로
   다른 트랜잭션과 잠금을 교차해서 기다릴 일이 없다 → 데드락 없음

### 각 설정이 무엇이고 왜 효과가 있었나 / 없었나

**① accept-count (접속 수락 대기열)** — 서버가 아직 `accept()` 하지 못한 TCP 연결을 OS 가 잠시 세워 두는 줄의 길이다.
줄이 꽉 차면 OS 가 새 연결을 거절한다("connection refused"). 100 → 5,000 으로 올렸지만 거절 수는 그대로였다.
원인은 Windows 가 이 줄을 **200 으로 제한**하기 때문이다. 파이썬으로 `listen(5000)` 소켓을 만들고 accept 없이 연결을 넣어 보면
정확히 200개째까지만 대기열에 들어가고 201번째부터 실패한다(`listen(200)` 과 동일). 즉 Tomcat 설정은 OS 에 의해 200 으로 잘린다.
Linux 에서는 `net.core.somaxconn`(기본 4096) 안에서 설정값이 그대로 적용되므로, 이 설정은 Linux 배포 시에는 의미가 있다.

**② 커넥션 풀 크기** — 서버가 MySQL 에 미리 열어 두고 돌려 쓰는 연결의 개수다. 3단계에서 HTTP 스레드 200개 중 190개가
커넥션을 기다리고 있었으므로, 풀을 키우면 동시에 DB 작업을 하는 요청이 늘어난다.

- 그러나 기대만큼 늘지 않았다. 풀을 늘리자 **행 락 대기 시간이 5초 → 65초 → 127초로 폭증**했다. 같은 강의의 신청은 `FOR UPDATE` 때문에 한 줄로 서야 하는데,
  커넥션이 많아지면 "커넥션을 쥔 채 락을 기다리는" 트랜잭션만 늘어난다. 줄 서는 장소가 커넥션 풀 앞에서 DB 행 락 앞으로 옮겨간 셈이다.
- 풀 30 이 풀 10 보다 나아 보이지 않은 것도 같은 이유다. 락 대기가 늘어난 만큼 커넥션 대기가 줄어든 효과가 상쇄됐다.

1. **Windows 접속 대기열 200 제한** — 오류의 전부가 여기서 난다. 애플리케이션 설정으로는 못 넘는다.

## 4단계-2: 락 구간 축소 결과

4단계-1에서 "같은 강의 행에 대한 락 경합"이 다음 병목으로 꼽혔다. 신청 트랜잭션 하나가 락을 쥔 채
여러 문장을 보내므로 락을 쥐는 시간이 길었다. 이번 단계에서는 **락을 쥐는 구간을 줄이는 것**이 목표다.

### 바꾸기 전에: 왜 이 방식이 락 시간을 줄이는가

2단계 방식(`SELECT ... FOR UPDATE`)의 신청 흐름은 이랬다. 번호는 DB 로 보내는 문장 순서다.

```
1. SELECT 학생                 (락 없음)
2. SELECT 강의 FOR UPDATE      ← 여기서 강의 행이 잠긴다
3. SELECT 중복 신청 여부
4. INSERT 신청 내역
5. UPDATE 강의 (enrolled_count = 자바가 계산한 값)
6. COMMIT                      ← 여기서 풀린다
```

강의 행은 2번부터 6번까지 잠겨 있다. 그 사이 자바는 DB 응답을 받고 → 다음 문장을 만들고 → 다시 보내기를 네 번 반복한다.
같은 강의를 신청하려는 다른 요청은 전부 2번 지점에서 이 과정이 끝나기를 기다린다.
은행 창구에 비유하면, 창구 직원이 손님 한 명의 서류를 들고 있는 동안 뒷줄 전체가 멈춰 있는 것과 같다.
줄이 줄어드는 속도는 "한 명을 처리하는 시간"에 달려 있으므로, 그 시간을 줄이는 것이 핵심이다.

조건부 UPDATE 방식은 2번과 5번(검사와 증가)을 DB 안에서 한 문장으로 처리한다.

```sql
update courses
   set enrolled_count = enrolled_count + 1
 where id = ? and enrolled_count < capacity
```

- `enrolled_count < capacity` 가 정원 검사다. 조건에 맞는 행이 없으면 아무것도 바꾸지 않는다.
- `enrolled_count + 1` 은 자바가 계산한 값이 아니라 **DB 가 지금 저장된 값에 더한다.** 다른 요청의 증가분을 덮어쓸 일이 없다.
- 실행 결과로 "바뀐 행 수"가 돌아온다. 1 이면 신청 성공, 0 이면 정원이 찬 것이다. 즉 검사 결과를 따로 읽어 올 필요가 없다.
- DB 는 이 UPDATE 를 실행하는 동안 행을 잠그고, 트랜잭션이 끝날 때 푼다. 자바가 "읽고 → 생각하고 → 쓰는" 왕복이 사라진다.

바꾼 뒤의 흐름은 이렇다.

```
1. SELECT 학생                 (락 없음)
2. SELECT 강의                 (락 없음, 이름/정원을 메시지에 쓰기 위해)
3. SELECT 중복 신청 여부        (락 없음)
4. UPDATE 강의 (조건부)         ← 여기서 잠긴다
5. INSERT 신청 내역
6. COMMIT                      ← 여기서 풀린다
```

잠긴 상태로 보내는 문장이 4개(3, 4, 5, 6)에서 3개(4, 5, 6)로 줄었다.

**주의할 점**

1. **INSERT 는 UPDATE 뒤에, 같은 트랜잭션 안에 있어야 한다.** INSERT 를 먼저 하면 2단계에서 본 데드락이 되살아난다.
   `enrollments` 가 `courses` 를 외래 키로 참조하므로 INSERT 는 강의 행에 공유 잠금(S)을 건다.
   두 요청이 S 를 쥔 채 UPDATE 의 배타 잠금(X)을 서로 기다리면 데드락이다. UPDATE(X)를 먼저 잡으면 INSERT 의 S 는 자기 것이라 문제없다.
   그래서 락 구간이 0 이 되지는 않는다. INSERT 와 COMMIT 은 여전히 락 안에 있다.
2. **정원이 찬 강의에 대한 UPDATE 도 행을 잠근다.** MySQL 기본 격리 수준(REPEATABLE READ)에서는 UPDATE 가 PK 로 찾은 행을
   조건(`enrolled_count < capacity`)이 안 맞아도 트랜잭션 끝까지 잠근다. 정원이 찬 뒤에 몰려오는 수천 건의 요청이
   "거절당하기 위해" 락 줄에 서는 셈이다. 이 문제는 아래 측정에서 실제로 드러났고, 락 없는 선검사로 해결했다.
3. **메모리의 Course 객체는 낡은 값을 갖는다.** 2번에서 락 없이 읽은 `enrolledCount` 는 UPDATE 이후의 값과 다르다.
   이 객체는 이름과 정원을 메시지에 쓰는 용도로만 쓰고, 값을 바꿔서 저장하면 안 된다. (바꾸면 JPA 가 UPDATE 로 덮어써서 갱신 유실이 다시 생긴다)
4. **강의 행 락이 사라지면 중복 신청 검사에 빈틈이 생긴다.** 아래에서 따로 다룬다.

### 같은 학생의 중복 신청은 어떻게 막나

2단계에서는 FOR UPDATE 가 같은 강의에 대한 모든 신청을 한 줄로 세웠기 때문에, "중복 검사(3번) → INSERT(4번)" 사이에
같은 학생의 다른 요청이 끼어들 수 없었다. 이제 3번은 락 없이 실행되므로 같은 학생의 요청 10개가 동시에 오면
10개 모두 "아직 신청 안 함"을 보고 INSERT 까지 갈 수 있다.

그래서 `enrollments` 테이블에 `(student_id, course_id)` **유니크 제약**을 걸었다 (`uk_enrollments_student_course`).
DB 는 같은 조합의 두 번째 INSERT 를 거부하고 `DataIntegrityViolationException` 을 던진다.
서비스는 이것을 잡아 `EnrollmentException("이미 신청한 강의입니다")` 로 바꾼다. 예외가 던져지면 트랜잭션이 롤백되므로
바로 앞 UPDATE 로 늘린 인원도 함께 되돌아간다.

코드의 `existsByStudentIdAndCourseId` 검사는 그대로 두었다. 대부분의 중복 신청(화면에서 두 번 누르기 등)은
여기서 걸려 락을 잡기 전에 거절되고, 동시에 들어온 경우만 유니크 제약까지 간다. 즉 **코드 검사는 1차, 유니크 제약이 최종** 이다.

유니크 제약은 Hibernate `ddl-auto: update` 가 기존 테이블에 자동으로 추가했다 (`SHOW CREATE TABLE enrollments` 로 확인).
기존 데이터에 중복 조합이 있었다면 추가에 실패했을 것이므로, 먼저 151행 / 151개 조합으로 중복이 없음을 확인했다.

### 수정 전후 코드 비교

**CourseRepository**

```java
// 수정 전 (2단계): 락을 걸고 읽는다
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select c from Course c where c.id = :id")
Optional<Course> findByIdForUpdate(@Param("id") Long id);

// 수정 후 (4단계-2): 검사와 증가를 한 문장으로. 반환값은 바뀐 행 수
@Modifying
@Query("update Course c set c.enrolledCount = c.enrolledCount + 1 "
        + "where c.id = :id and c.enrolledCount < c.capacity")
int increaseEnrolledCountIfNotFull(@Param("id") Long id);

@Modifying
@Query("update Course c set c.enrolledCount = c.enrolledCount - 1 "
        + "where c.id = :id and c.enrolledCount > 0")
int decreaseEnrolledCount(@Param("id") Long id);
```

**EnrollmentService.enroll()**

```java
// 수정 전 (2단계)
Student student = findStudent(studentId);
Course course = courseRepository.findByIdForUpdate(courseId)        // ← 락 시작
        .orElseThrow(...);
if (enrollmentRepository.existsByStudentIdAndCourseId(studentId, courseId)) {
    throw new EnrollmentException("이미 신청한 강의입니다: " + course.getName());
}
if (course.isFull()) {                                             // 자바가 검사
    throw new EnrollmentException("정원이 가득 찼습니다: ...");
}
course.increaseEnrolledCount();                                    // 자바가 더하고 JPA 가 UPDATE
return enrollmentRepository.save(new Enrollment(student, course)); // 커밋 때 락 해제

// 수정 후 (4단계-2)
Student student = findStudent(studentId);
Course course = courseRepository.findById(courseId)                 // 락 없는 일반 조회
        .orElseThrow(...);
if (enrollmentRepository.existsByStudentIdAndCourseId(studentId, courseId)) { // 1차 검사
    throw new EnrollmentException("이미 신청한 강의입니다: " + course.getName());
}
if (course.isFull()) {                                             // 락 없는 선검사 (②)
    throw new EnrollmentException("정원이 가득 찼습니다: ...");
}
int updated = courseRepository.increaseEnrolledCountIfNotFull(courseId); // ← 락 시작, 최종 검사 (①)
if (updated == 0) {
    throw new EnrollmentException("정원이 가득 찼습니다: ...");
}
try {
    return enrollmentRepository.save(new Enrollment(student, course));   // 커밋 때 락 해제
} catch (DataIntegrityViolationException e) {                            // 유니크 제약 = 최종 중복 검사
    throw new EnrollmentException("이미 신청한 강의입니다: " + course.getName());
}
```

**EnrollmentService.cancel()** 도 같은 방식으로 바꿨다. 락을 걸고 읽는 대신, 신청 내역을 먼저 지우고(`delete ... where id = ?`,
지운 행 수가 0 이면 "이미 취소됨") 실제로 지워졌을 때만 `enrolled_count - 1` UPDATE 를 보낸다.
같은 신청을 동시에 두 번 취소해도 인원이 두 번 줄지 않는다.

**Enrollment** 엔티티에 `@UniqueConstraint(name = "uk_enrollments_student_course", columnNames = {"student_id", "course_id"})` 를 추가했다.

### 왜 ① 만으로는 효과가 없었고 ② 는 효과가 있었나

**① 의 효과가 작았던 이유**

- 락 안의 문장이 4개에서 3개로 줄었을 뿐이다. INSERT 는 외래 키 때문에 UPDATE 뒤 같은 트랜잭션에 있어야 하고(주의할 점 1), COMMIT 도 락 안에 있다.
- 정원이 찬 강의에 대한 UPDATE 도 행을 잠근다(주의할 점 2). 실행 d 에서 UPDATE 2,246회 중 실제로 신청에 성공한 것은 151회이고,
  나머지 **2,095회는 "정원이 찼다"는 답을 듣기 위해 락 줄에 섰다가 롤백**했다. 2단계의 FOR UPDATE 도 똑같이 락을 잡고 거절했으므로, 이 부분은 달라진 게 없었다.
- 그래서 락 대기 횟수가 1,719 → 940 ~ 1,392 로 조금 줄고, 누적 시간은 실행에 따라 더 늘기도 했다.

**② 의 효과**

- 락 없이 읽은 `enrolled_count` 가 이미 정원과 같으면 UPDATE 를 보내지 않는다. 이 값은 조금 낡았을 수 있지만, 정원이 찬 강의는 누가 취소하기 전까지 계속 차 있으므로
  거절해도 틀리지 않는다. 혹시 그 사이에 자리가 났더라도 다음 요청이 가져가므로 정원이 비는 일은 없고, 반대로 낡은 값이 "안 찼음"이면 UPDATE 가 최종 판단을 한다.
- UPDATE 횟수가 2,246 → 239 로, 행 락 대기 횟수가 1,719(4단계-1) → 226 ~ 234 로 **87% 줄었다.** 누적 대기 시간도 126.8초 → 35 ~ 65초로 줄었다.
- 신청 p95 가 4,637 ms → 3,494 ~ 4,001 ms 로 나아졌고, 오류 비율도 범위 기준으로 조금 내려갔다.

**그래도 락 대기가 남는 이유** — ② 에서 UPDATE 1회당 평균 대기가 140 ~ 270 ms 다. 출발 직후 10개 강의마다 20여 건이 동시에 UPDATE 에 도착해 한 줄로 서기 때문에,
줄의 길이(약 24 ÷ 2 = 12 명분) × 한 건의 락 보유 시간으로 나뉘어 **한 트랜잭션이 락을 쥐는 시간은 약 20 ms** 로 추정된다. 50 VU 에서도 같은 계산(5명 줄, 평균 대기 49 ms)으로 약 20 ms 가 나온다.
이 20 ms 안에서 측정된 것은 COMMIT 이다. 세션 전체 누적으로 COMMIT 은 평균 3.7 ms 지만 **p95 28.8 ms, p99 69 ms, 최대 349 ms** 였다 (INSERT 는 p95 3.6 ms).
COMMIT 은 로그를 디스크에 쓰는 작업(`innodb_flush_log_at_trx_commit = 1`)이고, MySQL 이 Docker Desktop 의 가상 디스크 위에서 돌기 때문에 느리고 들쭉날쭉하다.
느린 COMMIT 하나가 그 강의 줄 전체를 멈춰 세운다 (행 락 최장 대기 1,773 ms).

### 목표(5,000 VU 오류 1% 미만, p95 3초 이내) → 달성하지 못함. 남은 병목과 근거

1. **Windows 접속 대기열 200 제한 (오류의 전부)** — 오류는 ①, ② 합쳐 12번 모두 `dial: connection refused` 뿐이다.
   애플리케이션 오류(5xx) 0건, 서버 로그 예외 0건, k6 의 `enroll_other` 0건. 4단계-1에서 확인한 대로 OS 가 수락 대기열을 200 으로 자르기 때문이며,
   코드나 설정으로는 넘을 수 없다. 오류 1% 미만은 Linux(Docker 컨테이너 등)에서 서버를 띄우거나, 앞에 리버스 프록시를 두거나, 접속을 몇 초에 걸쳐 분산해야 가능하다.
2. **PC 의 CPU 포화 (응답 시간의 상한)** — 5,000 VU 동안 CPU 88 ~ 94%, 2,000 VU 에서도 92%. 서버·MySQL·k6 가 한 PC 를 나눠 쓴다.
   락 대기를 87% 줄였는데도 p95 가 3.4 ~ 5.1초인 이유다. 락과 무관한 목록 조회(단순 SELECT, 서버 쪽 0.25 ms)조차 p95 2.2 ~ 5.1초가 걸린다.
   HTTP 스레드 200개 중 150개가 커넥션을 기다리는 것도 결국 "커넥션을 쥔 50개가 CPU 를 못 받아 느리게 끝나기" 때문이다. 풀을 더 키워도 CPU 가 없으면 소용없다(4단계-1의 풀 30 결과와 같은 이유).
   정확한 서버 한계는 k6 를 다른 머신에서 돌려야 보인다.
3. **COMMIT 의 디스크 쓰기 (남은 락 보유 시간의 주범)** — 위에서 본 대로 COMMIT p95 29 ms, 최대 349 ms. 같은 강의의 신청은 한 줄로 서므로 COMMIT 이 느리면 줄 전체가 기다린다.
   `innodb_flush_log_at_trx_commit = 2` 로 바꾸면 커밋마다 디스크에 쓰지 않아 빨라지지만, MySQL 이 죽으면 최근 1초의 커밋을 잃을 수 있는 트레이드오프가 있다.
   또는 MySQL 을 가상 디스크가 아닌 환경에서 띄우는 방법이 있다. 다만 이 병목은 신청 요청에만 영향을 주고(신청 p95 3.5 ~ 4.0초), 목록 조회의 느림은 설명하지 못한다.
4. **남은 락 경합 자체는 작다** — ② 에서 대기 226 ~ 234회. 더 줄이려면 외래 키를 없애 INSERT 를 락 밖으로 빼거나(락 안 문장 3 → 2), 강의별 요청을 큐로 직렬화하는 구조 변경이 필요한데,
   1 ~ 3번이 해결되기 전에는 체감 효과가 없을 것이다.

- `EnrollmentRepository`: `deleteByIdReturningCount()` 추가

## 4단계-3: Linux 컨테이너 실행 결과

4단계-1과 4단계-2에서 오류(connection refused)의 원인은 전부 **Windows 가 접속 수락 대기열을 200 으로 자르는 것**이었다.
이번에는 서버를 Linux 컨테이너에서 띄워 이 제한을 벗어나는지 확인한다.

### 구성

- `Dockerfile`: `eclipse-temurin:21-jdk-jammy` 이미지에 빌드된 jar 를 복사해서 실행한다. 컨테이너 안에서 Gradle 빌드를 하지 않으므로
  먼저 `gradlew bootJar` 로 jar 를 만들어야 한다. (`ss` 명령을 쓰기 위해 `iproute2` 를 설치한다)
- `docker-compose.yml` 에 `app` 서비스를 추가했다. `profiles: ["app"]` 이라서 평소 `docker compose up -d` 는 MySQL 만 띄우고,
  `--profile app` 을 붙일 때만 앱도 뜬다. 앱은 같은 compose 네트워크에서 `mysql:3306` 으로 직접 접속한다 (Windows 포트 포워딩을 거치지 않는다).
- Docker Desktop VM: CPU 6개, 메모리 8 GB, 커널 6.18 (WSL2).

```powershell
.\gradlew.bat bootJar
docker compose --profile app up -d --build       # MySQL + 앱 (앱은 load 프로필로 실행)
docker compose --profile app down                 # 둘 다 종료
```

### 실험 1: 컨테이너 안에서 accept-count 가 실제로 적용되는가

4단계-1에서 한 실험(listen 만 하고 accept 는 하지 않는 소켓에 연결을 계속 넣어 보기)을 `load-test/backlog_test.py` 로 옮겨
Windows 와 Linux 컨테이너에서 각각 돌렸다. 대기열이 꽉 차면 그 다음 connect 가 실패하므로, 성공한 연결 수가 곧 실제 대기열 크기다.

```powershell
python load-test\backlog_test.py 5000 6000                                                         # Windows
docker run --rm -v "${PWD}\load-test:/t:ro" python:3-alpine python /t/backlog_test.py 5000 6000    # Linux 컨테이너
```

| listen(n) | Windows (성공한 연결 수) | Linux 컨테이너 (성공한 연결 수) |
|---|---|---|
| 200 | 200 | 201 |
| 1,000 | **200** | **1,001** |
| 5,000 | **200** | **4,097** (`somaxconn` = 4096 에서 잘림) |

Windows 는 무엇을 요청하든 200 이고, Linux 는 요청한 값이 그대로 적용되며 상한은 `net.core.somaxconn`(컨테이너 안 기본값 4096)이다.
실패한 connect 의 종류도 다르다. Windows 는 즉시 거절(refused)하지만 Linux 는 SYN 을 버려서 클라이언트가 기다리게 된다(timeout). 즉 Linux 에서는 대기열이 넘쳐도 "거절"이 아니라 "지연"으로 나타난다.

실제 Tomcat 소켓도 확인했다. `ss -ltn` 의 Send-Q 열이 LISTEN 소켓에서는 접속 대기열 크기를 뜻한다.

```
$ docker exec course-registration-app ss -ltn
State  Recv-Q Send-Q Local Address:Port
LISTEN 0      1000               *:8080          ← application.yml 의 accept-count: 1000 이 그대로 적용됨
$ docker exec course-registration-app cat /proc/sys/net/core/somaxconn
4096
```

### 실험 2: Docker Desktop 의 포트 포워딩이 새로운 병목인가

k6 를 두 경로로 돌렸다.

- **포워딩 경유**: Windows 의 k6 → `localhost:8080` → Docker Desktop 중계 프로세스 → 컨테이너. 평소 브라우저로 접속하는 경로다.
- **Docker 네트워크 안**: k6 도 컨테이너(`grafana/k6`)로 띄워 compose 네트워크에서 `http://app:8080` 으로 직접 접속. 중계 프로세스를 거치지 않는다.

```powershell
# 포워딩 경유
k6 run -e VUS=5000 load-test/enroll.js
# Docker 네트워크 안
docker run --rm --network course-registration_default -v "${PWD}\load-test:/t:ro" grafana/k6 run -e VUS=5000 -e BASE_URL=http://app:8080 /t/enroll.js
```

두 경로 모두 매 실행 전 `reset.sql`, 실행 후 `verify.sql` 을 돌렸고, 컨테이너 안의 `/proc/net/netstat` 에서
`ListenOverflows`(접속 대기열이 넘친 횟수)의 실행 전후 차이를 함께 기록했다. Windows 의 8080 포트는 `netstat -ano` 로 확인한 결과
`com.docker.backend.exe` 가 듣고 있다. 즉 Windows 쪽에서 연결을 받는 것은 Tomcat 이 아니라 Docker Desktop 의 중계 프로세스다.

### connection refused 는 줄었는가, 왜인가

**Docker 네트워크 안: 거절 0.** 근거는 세 가지다.

1. 실험 1에서 Linux 는 `accept-count: 1000` 을 그대로 적용한다 (`ss` Send-Q 1000, `listen(1000)` → 1,001 연결).
2. 그 1,000 조차 넘친 적이 없다. 5,000 VU 3회 모두 컨테이너의 `ListenOverflows` 증가분이 0 이었다. Tomcat 의 acceptor 스레드가 연결을 받아 poller 에 넘기는 속도가
   5,000개가 몰려드는 속도보다 빠르고, 대기열 1,000 이 그 사이의 완충 역할을 충분히 했다.
3. 설령 넘쳤더라도 Linux 는 SYN 을 버려서 클라이언트를 기다리게 하지 "거절"하지 않는다 (실험 1의 timeout). 그래서 k6 는 오류 대신 긴 응답 시간을 봤을 것이다.

**포워딩 경유: 거절이 오히려 늘었다 (4단계-2의 28 ~ 38% → 82 ~ 89%, 500 VU 에서도 0% → 41%).** 근거는 다음과 같다.

1. 컨테이너의 `ListenOverflows` 는 0 이다. 거절은 컨테이너에 도달하기 전, 즉 Windows 쪽에서 일어났다.
2. Windows 의 8080 포트를 듣는 것은 `com.docker.backend.exe` 다. Windows 프로세스이므로 접속 대기열은 똑같이 200 으로 잘린다 (실험 1의 Windows 열).
3. 4단계-2의 Tomcat(Windows 네이티브)은 대기열 200 을 비우는 일이 "연결을 받아 poller 에 등록"하는 것뿐이었지만, Docker Desktop 중계 프로세스는 연결 하나마다
   VM 안의 컨테이너로 **새 연결을 하나 더 열어야** 한다. 200 짜리 대기열을 비우는 속도가 Tomcat 보다 느려서 같은 대기열 크기에서도 더 많이 넘친다 (이 부분은 측정이 아니라 동작 원리에서 나온 추정이다).

정리하면 Linux 컨테이너는 접속 대기열 문제를 **완전히 해결**했고, 남은 거절은 전부 "Windows 에서 컨테이너로 들어가는 문"인 Docker Desktop 포트 포워딩에서 생긴다.
포트 포워딩은 새로운 병목이 맞다. 다만 이것은 이 노트북에서 Windows 쪽 클라이언트가 컨테이너에 접속할 때만 생기는 문제이고, 서버를 실제 Linux 서버에 배포하면 존재하지 않는 경로다.

### 그 밖에 달라진 것

- **DB 왕복 경로가 짧아졌다.** 4단계-2까지 앱(Windows)은 `localhost:3306` → Docker Desktop 중계 → MySQL 컨테이너로 접속했지만, 이제 같은 VM 안에서 직접 접속한다.
  5,000 VU 에서 COMMIT 평균이 1.3 ~ 2.5 ms → 0.6 ~ 1.0 ms 로, 행 락 누적 대기가 35 ~ 65초 → 18 ~ 24초로 줄었다. (락 대기 횟수 자체도 226 ~ 234 → 124 ~ 152)
- **서버가 처리한 일은 늘었다.** 4단계-2에서는 7,200 ~ 7,800 요청만 서버에 닿았는데 이제 10,000 요청을 전부 처리하면서 p95 는 비슷한 범위(3.8 ~ 5.5초)다.
  초당 처리는 663 ~ 985 → 1,010 ~ 1,252 로 늘었다.

### 목표 대비: 오류 1% 미만 → 달성 (Docker 네트워크 안 0%), p95 3초 이내 → 미달 (3.8 ~ 5.5초)

이 노트북 한 대 환경에서 **더 개선할 수 있는 것**:

1. **요청당 CPU 작업 줄이기.** 5,000 VU 동안 앱 컨테이너가 약 4코어(363 ~ 409%)를 쓰고 PC 전체가 90% 다. 응답 시간은 이제 순수하게 "CPU 를 기다리는 시간"이다.
   요청의 절반인 강의 목록 조회는 매번 DB 를 읽고(5,000 VU 한 번에 SELECT 20,008회 중 5,000회) JSON 으로 바꾸는데, 목록을 짧은 시간(예: 1초) 캐시하면
   이 요청들이 커넥션 풀 줄에 서지 않게 된다. 3초 시점에 HTTP 스레드 104 ~ 149개가 커넥션을 기다리고 있었고, 그중 상당수가 목록 조회다.
   신청 쪽은 학생 조회·강의 조회·중복 검사 세 SELECT 를 줄이거나 합칠 여지가 있다.
2. **부하 발생기를 네트워크 안에서 돌리기.** 측정 방법의 문제이긴 하지만, 이 PC 에서 서버 자체의 한계를 보려면 앞으로는 k6 를 Docker 네트워크 안에서 돌려야 한다.
   포워딩 경유 숫자는 서버가 아니라 Docker Desktop 의 한계를 재는 것이다.
3. **COMMIT 디스크 쓰기** (`innodb_flush_log_at_trx_commit = 2`): 4단계-2에서 지목했지만, 지금은 COMMIT 평균이 1 ms 안팎이고 락 누적 대기도 20초 안팎이라 효과가 작을 것이다. 우선순위 낮음.

**이 환경에서는 개선할 수 없는 것**:

1. **CPU 총량.** 6코어를 앱(약 4) + MySQL(약 1.3) + k6(0.4 ~ 0.9)가 나눠 쓴다. 부하 발생기가 같은 PC 에 있는 한 서버가 쓸 수 있는 CPU 는 4코어 남짓이고,
   초당 1,000 ~ 1,250 요청이 그 상한이다. 설정으로는 안 움직이며, 정확한 서버 한계는 k6 를 다른 머신에서 돌려야 보인다.
2. **Windows 에서 컨테이너로 들어가는 경로.** Windows 의 접속 대기열 200 제한과 Docker Desktop 포트 포워딩은 OS 와 Docker Desktop 의 동작이라 앱 설정으로 바꿀 수 없다.
   브라우저 같은 Windows 쪽 클라이언트가 동시에 수천 개 연결을 열면 여전히 거절된다. 실제 Linux 서버에 배포하면 이 경로 자체가 없다.
3. **Docker Desktop 가상 디스크** 위의 MySQL 은 그대로다. 다만 위에서 본 대로 지금은 병목 순위가 낮다.

## 4단계-4: 목록 캐시 결과

4단계-3에서 오류는 0 이 됐지만 p95 는 3.8 ~ 5.5초였고, 원인은 CPU 포화(앱 약 4코어)였다.
이번에는 요청당 CPU 와 DB 작업을 줄인다. 핵심은 **강의 목록 조회를 1초 동안 메모리에 캐시**하는 것이고,
신청 전에 보내던 SELECT 도 줄였다. Redis 같은 외부 캐시는 쓰지 않고 애플리케이션 메모리(자바 객체)에 둔다.

### 바꾸기 전에: 캐시가 왜 효과가 있는가

4단계-3의 5,000 VU 한 번(요청 10,000개)에서 DB 로 보낸 SELECT 는 20,008번이었다.

| SELECT 종류 | 횟수 | 설명 |
|---|---|---|
| 강의 목록 | 5,000 | 요청의 절반. 누가 보든 똑같은 10줄 |
| 학생 조회 | 5,000 | 신청 때 학생이 존재하는지 확인 |
| 강의 조회 | 5,000 | 신청 때 이름/정원을 읽고 정원 선검사 |
| 중복 검사 | 5,000 | 같은 강의를 이미 신청했는지 |

강의 목록 요청 하나는 "커넥션 풀 줄 서기 → SELECT → Hibernate 가 엔티티로 변환 → DTO 로 변환 → JSON" 을 매번 거친다.
10줄짜리 똑같은 결과를 초당 1,000번 넘게 만드는 셈이다. 1초에 한 번만 DB 에서 읽고 나머지 요청에는 메모리의 같은 결과를 돌려주면,
목록 요청 5,000개가 **커넥션 풀 줄에 서지 않고, SQL 도 보내지 않고, 변환도 하지 않는다.**
4단계-3에서 실행 3초 시점에 HTTP 스레드 104 ~ 149개가 커넥션을 기다리고 있었는데 그 상당수가 목록 조회였다.

같은 캐시를 신청 쪽에서도 쓴다. 신청 전의 "강의가 존재하는가 / 정원이 찼는가" 검사를 DB 대신 캐시로 하면 강의 조회 5,000번이 사라진다.
정원이 찬 강의에 대한 요청(5,000 VU 에서 4,849건)은 **트랜잭션도, 커넥션도, SQL 도 없이** 캐시만 보고 즉시 거절된다.

### 바꾸기 전에: 화면의 신청 인원이 최대 1초 늦게 보이는 것은 괜찮은가

괜찮다. 이유는 두 가지다.

1. **목록의 숫자는 참고용이고, 정원을 지키는 것은 DB 다.** 화면이 "29/30" 이라서 신청을 눌렀는데 그 사이 찼다면 DB 의 조건부 UPDATE 가 거절하고
   "정원이 가득 찼습니다" 를 돌려준다. 캐시 없이도 "화면을 본 순간"과 "신청 버튼을 누른 순간" 사이에는 늘 틈이 있었다. 1초 캐시는 그 틈을 조금 늘릴 뿐이다.
   실제 수강신청 사이트도 화면의 잔여 인원이 실시간이 아니다.
2. **반대 방향(자리가 났는데 "찼음"으로 보이는 것)은 짧게 끝난다.** 취소가 일어나면 캐시를 바로 비우므로 다음 요청부터 새 값을 본다.
   또 DB 가 "정원 참"이라고 답한 순간에도 캐시를 비워서, 캐시가 "안 참"이라고 잘못 알고 있는 시간을 줄인다.

받아들이기 어려운 경우가 있다면 "정원 마감 직전 1초의 숫자가 정확해야 하는" 서비스일 텐데, 이 서비스의 사용자는 어차피 신청 결과로 판단하므로 해당하지 않는다.

### 바꾼 내용

**`CourseListCache` (새 클래스)** — 강의 목록 DTO 를 1초 동안 보관한다.

- 대부분의 요청은 `volatile` 필드 하나를 읽고 끝난다 (DB, 커넥션, 락 모두 없음).
- 1초가 지나면 **한 스레드만** DB 를 읽고(`ReentrantLock.tryLock`), 그동안 다른 스레드는 직전 값을 그대로 쓴다.
  처음에는 `synchronized` 로 모두 기다리게 만들었는데, 부하 중 스레드 덤프에서 56 ~ 86개 스레드가 그 한 번의 DB 읽기를 기다리며 멈춰 있는 것이 보여서 바꿨다 (아래 측정 ① 참고).
- `invalidate()` 는 "다음 요청이 새로 읽어라" 표시만 남긴다. 취소 후, 그리고 DB 가 정원이 찼다고 알려줬을 때 호출한다.

**`EnrollmentService.enroll()`** — SQL 을 다섯 문장에서 세 문장으로 줄였다.

```
4단계-3                                   4단계-4
1. SELECT 학생                            (없음: INSERT 의 외래 키 검사가 대신한다)
2. SELECT 강의 (정원 선검사, 이름)         (없음: 캐시에서 읽는다. 정원이 찼으면 여기서 끝, SQL 0개)
3. SELECT 중복 검사                        1. SELECT 중복 검사
4. UPDATE 조건부 (락 시작)                 2. UPDATE 조건부 (락 시작)
5. INSERT                                 3. INSERT
6. COMMIT                                 4. COMMIT
```

- `@Transactional` 을 메서드에서 떼고 `TransactionTemplate` 으로 DB 가 필요한 구간만 감쌌다. `@Transactional` 은 메서드에 들어오는 순간 커넥션을 잡는데,
  정원이 찬 강의에 대한 요청은 커넥션이 필요 없기 때문이다.
- 학생/강의 엔티티는 `getReferenceById()` 로 "ID 만 아는 껍데기 객체"를 만들어 INSERT 에 넘긴다 (SELECT 없음).
  존재하지 않는 학생이면 INSERT 의 외래 키 검사가 실패하고, 어떤 제약에 걸렸는지(`uk_enrollments_student_course` 인지 `student_id` 인지) 보고 메시지를 정한다.
- 응답(`EnrollmentResponse`)은 캐시의 강의 정보로 만든다. 껍데기 객체의 이름을 읽으려 하면 SELECT 가 나가기 때문이다.
- 정원 검사 순서: 캐시 선검사(SQL 없음) → 중복 검사 → **DB 조건부 UPDATE(최종)**. 정원은 항상 DB 기준으로 지켜진다.
  부작용 하나: 이미 신청한 학생이 정원이 찬 강의를 다시 누르면 "이미 신청" 대신 "정원 가득" 메시지를 본다. 둘 다 거절이므로 그대로 뒀다.

**`EnrollmentConcurrencyTest`** — `@BeforeEach` 에서 DB 를 직접 되돌린 뒤 캐시도 새로 읽는다. (그러지 않으면 앞 테스트가 남긴 "정원 참"이 1초 동안 보인다)

### 무엇이 좋아졌고, 무엇이 나빠졌나

**좋아진 것**

- SELECT 가 20,008 → 약 500 으로 97% 줄었고, CPU 평균이 90% → 65% 로 내려왔다. 응답 시간이 "CPU 를 기다리는 시간"이었으므로 p95 가 절반 이하로 줄었다 (3.8 ~ 5.5초 → 1.6 ~ 2.6초).
- 초당 처리가 약 1,100 → 2,200 으로 두 배가 됐다. 서버가 같은 10,000 요청을 절반 시간에 끝낸다.
- 목록 조회는 더 이상 커넥션 풀 줄에 서지 않는다. 4단계-3에서 풀 대기 104 ~ 149 스레드였던 것이 ② 에서 0 ~ 123 으로 실행에 따라 들쭉날쭉한데,
  남은 대기는 전부 신청 요청(UPDATE 를 보내려는 스레드)이다.

**나빠진 것: 락 대기가 늘었다 (124 ~ 152회 / 18 ~ 24초 → 388 ~ 448회 / 109 ~ 123초)**

4단계-3에서는 신청마다 DB 에서 강의를 새로 읽어 정원 선검사를 했으므로, 강의가 찬 뒤 오는 요청은 거의 전부 UPDATE 전에 걸러졌다 (UPDATE 184 ~ 197회 ≈ 성공 151 + 약간).
이제 선검사는 최대 1초 낡은 캐시로 하므로, **강의가 찬 뒤 캐시가 갱신되기 전까지 들어온 요청은 UPDATE 까지 가서 락 줄에 선다** (UPDATE 456 ~ 599회).
게다가 서버가 두 배 빨라져 같은 시간에 두 배 많은 요청이 UPDATE 에 도착한다. 줄이 길어진 만큼 한 건당 대기(UPDATE 평균 186 ~ 270 ms)도 늘었다.
DB 가 "정원 참"이라고 답하면 캐시를 비우는 ② 의 처리로 ① 보다는 줄었지만(UPDATE 최대 704 → 599, 락 누적 최대 160 → 123초), 4단계-3 수준으로 돌아가지는 않았다.

락을 쥐는 시간 자체도 눈에 띈다. COMMIT 평균이 17 ~ 20 ms 인데, 4단계-3의 0.6 ~ 1.0 ms 와 직접 비교하면 안 된다.
4단계-3의 COMMIT 5,151회 중 5,000회는 목록 조회의 읽기 전용 트랜잭션(디스크 쓰기 없음)이라 평균을 끌어내렸고, 지금은 목록 조회가 트랜잭션을 열지 않아
COMMIT 160 ~ 175회가 전부 실제 INSERT 의 커밋(디스크 쓰기)이다. 즉 **신청 한 건이 락을 쥔 채 커밋에 쓰는 시간은 원래부터 약 20 ms** 였고, 이것이 줄의 속도를 정한다.

**① 에서 본 두 가지 함정** (② 에서 고침)

- `synchronized` 갱신: 실행 3초 시점에 56 ~ 86개 스레드가 캐시 모니터에서 BLOCKED 상태였다. 갱신하는 한 스레드가 커넥션 풀 줄(61 ~ 79개 대기)에 서 있는 동안 나머지가 전부 멈춘 것이다.
  갱신 중에는 직전 값을 쓰게 바꾸자 사라졌다.
- ① 의 첫 5,000 VU 실행에서 컨테이너 `ListenOverflows` 가 357 이었다. 앱 컨테이너가 609%(6코어 전부)를 쓰는 동안 Tomcat 의 acceptor 스레드가 CPU 를 못 받아 대기열 1,000 이 넘쳤다.
  Linux 는 넘친 SYN 을 버리고 클라이언트가 1초 뒤 재시도하므로 오류가 아니라 지연(그 실행의 p95 3,011 ms)으로 나타났다. 4단계-3 "실험 1"의 설명 그대로다. ② 에서는 CPU 여유가 생겨 0 이었다.

### 목표(5,000 VU 오류 1% 미만, p95 3초 이내) → 달성 (오류 0.0%, p95 1,629 ~ 2,563 ms, 3회 모두)

### 다음 병목 (근거)

1. **같은 강의 행의 락 줄** — 신청 p95 1.4 ~ 1.8초의 대부분이 UPDATE 대기(평균 186 ~ 270 ms, 388 ~ 448회)다. 줄의 속도는 "한 건이 락을 쥔 시간 ≈ COMMIT 의 디스크 쓰기 약 20 ms" 가 정하고,
   줄의 길이는 "캐시가 낡은 동안 UPDATE 까지 온 요청 수"가 정한다. 둘 중 하나를 줄여야 한다. 커밋 쪽은 `innodb_flush_log_at_trx_commit = 2`(MySQL 이 죽으면 최근 1초 커밋 유실 가능)가 가장 간단하고,
   줄 길이 쪽은 강의가 찼다는 사실을 캐시에 더 빨리 반영하거나(예: 성공한 신청이 마지막 자리였는지 UPDATE 결과로 알아내기), 강의별로 앱 안에서 먼저 줄을 세우는 방법이 있다.
2. **CPU** — 평균 65% 지만 최고는 여전히 98 ~ 99% 다. 출발 직후 5,000 연결이 한꺼번에 들어오는 순간에는 아직 포화다. 남은 요청당 작업은 JSON 변환과 HTTP 처리, 그리고 신청의 SQL 세 문장이다.
3. **측정 환경** — k6 자체가 0.4 ~ 1.2코어를 쓴다. 이 PC 에서 서버 한계를 더 정확히 재려면 k6 를 다른 머신에서 돌려야 한다 (4단계-3과 같음).
