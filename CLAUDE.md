# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A course-registration (수강신청) site built as a **staged learning project** on concurrency and load handling:
Java 21 + Spring Boot 4.1 + Spring Data JPA + MySQL 8.4 (Docker). No auth; the UI takes a student ID (1~5000).

The README is the project log. Each stage appends a results section (before/after tables, bottleneck analysis,
"next bottleneck" reasoning). Stages so far: 1 basic features → 2 reproduce race, fix with pessimistic lock →
3 k6 load test baseline → 4-1 Tomcat accept-count / Hikari pool tuning → 4-2 replace the lock with a
conditional UPDATE plus a unique constraint → 4-3 run the app in a Linux container. **When a stage is completed, append
its measurements and reasoning to README.md in the same style** and commit with a `N단계: ...` message.

Conventions: all code comments, README, test names, and commit messages are in Korean and written for a
beginner (explain *why*, not just what). Keep that style. Before changing concurrency behavior, let the user
reproduce the problem first; the project's point is observing the failure before fixing it.

## Commands

MySQL must be running before `bootRun` or any test (the test hits the real DB, there is no H2/Testcontainers).

```powershell
docker compose up -d                 # MySQL on localhost:3306 (user app / app1234, db course_registration)
.\gradlew.bat bootRun                # app on http://localhost:8080 (SQL logging on)
.\gradlew.bat test --tests "*EnrollmentConcurrencyTest" --rerun   # the only test; --rerun forces re-execution
.\gradlew.bat bootJar                # build\libs\course-registration-0.0.1-SNAPSHOT.jar
docker compose down -v               # also wipes the DB volume
```

In the Bash tool, `JAVA_HOME` may need to point at the JDK 21 install before `./gradlew` works.

Load test (requires k6; run the jar with the `load` profile, which only turns SQL logging off):

```powershell
java -jar build\libs\course-registration-0.0.1-SNAPSHOT.jar --spring.profiles.active=load
docker exec -i course-registration-mysql mysql -uapp -papp1234 course_registration < load-test/reset.sql
k6 run -e VUS=500 load-test/enroll.js        # VUS = number of virtual users = distinct student IDs
docker exec -i course-registration-mysql mysql -uapp -papp1234 course_registration < load-test/verify.sql
```

`reset.sql` wipes all enrollments; `verify.sql` must report `over_capacity = 0` and `mismatch = 0` after every
run. The k6 script counts HTTP 400 "정원" (capacity-full) responses as expected, not as errors.

Containerized app (stage 4-3). The Dockerfile only copies the jar, so build it first. The `app` service sits
behind a compose profile so plain `docker compose up -d` still starts only MySQL:

```powershell
.\gradlew.bat bootJar
docker compose --profile app up -d --build       # app on :8080 with the load profile, talks to mysql:3306
docker compose --profile app stop app
# measure WITHOUT Docker Desktop's port proxy: run k6 inside the compose network
docker run --rm --network course-registration_default -v "${PWD}\load-test:/t:ro" grafana/k6 run -e VUS=5000 -e BASE_URL=http://app:8080 /t/enroll.js
```

k6 from Windows against the container goes through `com.docker.backend.exe`, whose Windows-side listen
backlog is capped at 200 and refuses 80%+ of a 5,000 VU burst. Those numbers measure Docker Desktop, not the
server. `load-test/backlog_test.py` reproduces the backlog cap on either OS.

## Architecture

Request flow: `static/index.html` (vanilla JS) → `controller` → `EnrollmentService` → Spring Data repositories → MySQL.
Schema is generated by Hibernate `ddl-auto: update` from the three entities (`courses`, `students`, `enrollments`).

Everything interesting is in `EnrollmentService.enroll()` / `cancel()`:

- `Course.enrolledCount` is a denormalized counter that must always equal the number of `enrollments` rows for
  that course. The concurrency test and `verify.sql` both assert this invariant.
- Capacity is enforced by one conditional statement, `CourseRepository.increaseEnrolledCountIfNotFull()`
  (`UPDATE ... SET enrolled_count = enrolled_count + 1 WHERE id = ? AND enrolled_count < capacity`); 0 rows
  affected means full. The course row is locked only from that UPDATE to commit. Before it, the service does
  lock-free reads (student, course, duplicate check) and a lock-free `isFull()` pre-check so requests to a
  full course never touch the row lock. Never load the Course entity and write its counter back: the entity
  is stale after the UPDATE and a dirty flush would reintroduce the lost-update bug.
- **Statement order matters**: the UPDATE on `courses` must precede the INSERT into `enrollments`. The
  INSERT takes a shared FK lock on the course row; doing it first recreates the stage-2 deadlock.
- Duplicate enrollment is finally enforced by the DB unique constraint `uk_enrollments_student_course`;
  the service translates `DataIntegrityViolationException` into `EnrollmentException` (the transaction
  rolls back, undoing the counter increment). The `existsBy...` check is only a fast path for messages.
- `cancel()` deletes via `deleteByIdReturningCount()` and decrements only when a row was actually deleted.
- Rule violations throw `EnrollmentException` → `GlobalExceptionHandler` → HTTP 400 `{"message": "..."}`.
  Clients (UI, k6 script) match on the Korean message text (e.g. "정원"), so don't reword messages casually.

`DataInitializer` seeds 10 courses (capacities summing to 151) and tops up students to 5,000 on every startup.
The concurrency test relies on `CS101` having capacity 30 and resets only that course's rows before running.

Tuning knobs live in `application.yml` with comments recording why each value was chosen (Hikari pool 50,
Tomcat accept-count 1000). Known local limits (stages 4-1 to 4-3): on Windows the listen backlog is capped at
200 so accept-count only takes effect inside the Linux container (verified with `ss -ltn`, Send-Q 1000); with
k6 inside the Docker network errors drop to 0% but p95 stays 3.8 to 5.5 s because CPU saturates near 90%
(app ~4 cores, MySQL ~1.3, k6 the rest). Useful evidence sources: `Innodb_row_lock_waits/_time` deltas,
`performance_schema.events_statements_summary_by_event_name` (truncate before a run), `ListenOverflows` in
the container's `/proc/net/netstat`, `docker stats`, and `docker exec course-registration-app jcmd 1
Thread.print` at ~3 s into a 5,000 VU run.
